# 아발론 현재 방향과 작업 상태

2026-10-06 기준 요약. 작업일지와 관련 세션을 읽은 시점의 상태이며 실시간 운영 점검 결과는 아니다. 상세 변경 이력은 최상위 `작업일지.md`를 계속 사용한다.

## 사용자 목표와 최근 방향

사람 한 명이 역할과 의도를 가진 AI 네 명과 아발론을 플레이한다. 핵심 고민은 자연스러운 토론과 정체·의도를 숨기는 전략적 행동이다. 현재 5인 게임이며 잘 동작하면 7인으로 확장하려는 계획이 있다.

사용자는 기존 코드 중심 진행보다 JEV를 사용하면 더 자유로운 대화와 진행이 가능하다고 보아 JEV를 도입한 뒤 충신·멀린을 개선하려 했다. 따라서 JEV 기존 코드 비교의 우위를 먼저 입증해야만 도입하는 방향으로 잡았던 Codex 권고는 정정했다. 자유로운 대화 효과는 사용자 기대이며 측정된 성과는 아니다.

현재 역할 AI 판단과 대사 생성은 Gemini가 담당하고, JEV는 대화 제어를 맡는 구조다. 합법 행동·상태 전이·비밀정보 경계는 게임 엔진이 검증한다. 현재 JEV가 역할별 전략이나 팀/투표/카드 결정을 모두 대신하는 것으로 표현하면 안 된다.

## 다른 세션의 최신 진행 작업

JEV 관련 세션에서 사용자가 채팅 내 찬반/임무 행동 버튼, JEV 진행 시점 판단, 제한된 AI 간 연속 토론을 논의했다. 이어 판당 Gemini/JEV 토큰과 비용 표시, JEV 도입 버전 제작·배포, 이전 버전 보관을 요청했다. 확인 당시 해당 턴은 진행 중이었다. 완성·배포 성공·세부 동작은 아직 이 요약에서 확인하지 않았다.

기존 발언자 선택 JEV의 배포 완료와 새 진행 구조의 배포 완료는 서로 다른 상태다. 단계 전환과 필수 표 제출은 엔진 규칙 검증을 유지해야 하며, 연속 토론의 사람 개입·발언 상한·실패 대체가 설계/검증 대상이다.

## AI 개선 후보와 결과의 한계

사람 같은 AI를 위한 V3 프롬프트와 로컬 프로토타입이 별도 세션에서 만들어졌다. 운영 V2 전체 교체와 품질 개선 검증은 완료로 기록하지 않는다. 로컬 실제 모델 연결 상태는 별도 확인이 필요하다.

과거 구체적 발언을 유도한 프롬프트 후보는 실제 소규모 평가에서 기대 품질을 충족하지 못해 운영에 채택하지 않은 기록이 있다. 규칙·형식·정보 경계 자동 검사 통과와 전략/자연스러움 검증은 구분한다.

확률모형 계수 학습, 충신/멀린 개선의 확증 평가, 자동 대국으로 얻은 승률 개선은 아직 결과가 없다. 이전 설계·구현·연결 smoke를 모델 성능 향상으로 표현하지 않는다.

## 평가 방향

| 대상 | 추천 수치 | 해석 |
| --- | --- | --- |
| 충신 | 확정 정보 해석 정답률, AI 자체 악 확률의 Brier | 팀에 악을 넣었다는 이유만으로 전략을 오답 처리하지 않음. 서버 계산값이 아니라 AI 자체 판단을 채점 |
| 멀린 | 원정 단계 통과율, 암살 회피율, 최종 선 성과 | 암살 회피만 좋아지고 원정을 돕지 못하는 후보를 구별. 고정 공격자/충신/라우팅 조건 필요 |
| JEV | 발언자/WAIT 적합률, 필요한 응답 누락, 불필요 발언 | 의미 사례는 사전 허용 후보 레이블 필요. 규칙 검사는 자동화. 사용자 전수 채점은 필수 아님 |
| 운영 | 오류·대체율, 응답 지연, 전체 토큰·비용 | 실패·재시도·폐기도 포함. 로그에 없는 사용량을 0으로 처리하지 않음 |

처음 논의한 보조정보 여부×JEV 여부 네 조합은 개별 효과·상호작용을 나누는 설계다. 최신 사용자 방향에서는 JEV를 도입 전제로 고정한 뒤 역할 개선을 비교할 수 있다. 역할 후보를 만든 후 충신 기본/개선×멀린 기본/개선 조합으로 협력 효과를 검증하는 안은 Codex 제안이며 아직 실행되지 않았다.

## 발표 전 우선순위

사용자가 10월 8일 발표를 앞두고 있다. 최신 권고는 JEV 기반 진행의 기준 버전을 정리/고정하고, 충신의 동일 상태 기존/후보 추론 평가를 우선해 소규모 정량 결과를 확보하는 것이다. 시간·비용이 허용하면 멀린의 고정 공격자 식별 평가를 탐색적으로 추가한다. 전체 선 승률/암살 회피의 일반적인 개선 확증까지 이틀 안에 보장하지 않는다.

아직 정할 사항은 충신 개선의 정확한 범위(프롬프트/보조정보/둘의 묶음), 개발/보류 평가 사례, 모델·조건·반복, 호출 비용 범위, 채택 기준이다. 어떤 개선 수치도 아직 측정하지 않았다.

### 지금 사용자가 할 일: 첫 2~3판은 플레이 점검

2~3판은 운영 문제 발견을 위한 제안이며 통계적 충분 표본이나 비용 실행 승인이 아니다. 먼저 현재 기본 구성 하나로 플레이한다. 모델/프롬프트/확률 입력을 판마다 바꾸지 않는다.

1. 새 게임에서 역할 안내와 실제 모델 연결/선택 모드를 확인한다. 기존 진행 중 판은 새 설정을 따르지 않을 수 있다.
2. 평소처럼 플레이하되, 한 번은 AI를 지목해 팀 선정 이유를 묻고, 한 번은 공개 투표/원정 결과와 다른 주장을 지적한다. 답변이 실제 질문·공개 사건에 맞는지 본다.
3. AI 대화가 멈춘 뒤 다음 단계 버튼으로 진행할 수 있는지 확인한다. 정상 WAIT/자율 SILENCE와 오류 안내/멈춤을 구분한다.
4. 가능한 경우 새로고침 후 같은 판/선택 상태가 유지되는지 확인한다. 새 게임으로 넘어가기 전 역할 추측 제출→승패/암살→정답 공개→JSON 다운로드를 끝낸다. 보기 드문 5회 부결 등을 일부러 만들 필요는 없으며 규칙 경로는 자동 검사와 별도 시나리오로 보완한다.
5. 판 ID와 가장 불편했던 장면 1~3개를 남긴다. `단계/사건 버전 또는 시각 / 실제 행동 / 기대 행동 / 심각도`면 충분하다. 대기 시간은 초시계로 잰 경우만 수치로 적고 느낌은 체감으로 구분한다. 이 채팅에 주면 프로젝트 기록은 작업일지 한 파일에 연결한다.
6. 완료 로그의 판 ID, 실제 모델/프롬프트/라우팅/역할 추측 버전, modelUsage, unknownCalls, 추측 결과를 확인한다. 비정상 판도 버리지 않고 중단 이유와 진단 로그를 보존한다. 로그 원문은 Git 공개 대상에서 제외된 logs/에 둔다.

파일이 존재하는 것만으로 사용량 완전성을 보장하지 않는다. 상시 수집과 늦은 사용량 갱신 문제를 해결하기 전에는 종료 후 요청이 끝난 시점의 수동 다운로드를 우선 사용한다.

### 이후 개발과 평가 순서

1. **수집과 기준 고정:** 위 수집 문제 보완, 현재 배포/소스/판별 버전 일치 확인. 신규 한 판의 서버→JSON→비교기 연결까지 확인하면 완료.
2. **게임 안정화:** 첫 플레이에서 진행 불가·상태 유실·비밀 정보의 시스템 유출을 최우선으로 재현/수정한다. 이어 무응답·반복·사실 오류·발언과 행동 불일치를 고친다. 악의 의도적인 거짓말과 모델의 공개 사실 착각을 구분한다. 수정 사례마다 실패 전/후 자동 검사와 사람 재확인을 남긴다.
3. **구성 비교:** 안정된 버전에서 Gemini 단독과 JEV+Gemini를 균형 있게 번갈아 플레이한다. 프롬프트/확률 입력은 고정하고 사용자 역할과 실행 순서를 기록한다. 판수·비용 상한은 실제 판당 비용/소요 시간을 본 뒤 정한다. 최초 소수 표본은 탐색으로 보고 완료/중단/오류, 추정 비용/누락, 대화 경험을 함께 본다. 승률/사용자 식별률로 성급히 우열을 확정하지 않는다.
4. **확률 보조 실험:** 앞 단계의 기준 구성에서 확률 입력 ON/OFF 범위를 정하고 구현한다. 현재 스위치는 없다. 자기 역할·합법 시작 정보·공개 사실은 유지하고 Gemini/JEV 및 기억 경로를 검사한다. 고정된 관찰 사례의 선택 변화와 실제 판의 결과를 구분한다.
5. **프롬프트 개선:** 실제 문제 장면을 역할별 고정 평가 사례로 만든다. 공개 사실 정확성, 질문 응답, 역할 목표, 불필요한 반복과 일관성의 기대 행동을 적고 이전/개선 프롬프트를 동일 조건에서 비교한다. 예산/반복 수/통과 기준은 호출 전에 정하며 모의 검사와 실제 모델 평가를 구분한다.
6. **확장과 포트폴리오:** 5인 핵심 흐름이 안정된 뒤 7인/추가 역할을 검토한다. 문제→로그 근거→선택 이유→변경→재검증→잔여 한계를 정리한다. 외부 사용자 평가는 접근 권한과 데이터 보관 범위를 정한 다음 진행한다.

사용자 식별률은 기존에 확정한 은폐 목적에 따라 해석하되 승률과 분리한다. 시작부터 알고 있는 진영이 점수에 포함되므로 사용자 시작 역할별 결과를 우선 보고, 미지 항목만의 채점은 별도 보완 대상이다. 완성도 판단에서 재미/대화 품질은 사용자의 직접 플레이 확인이 필요하다.
