# 아발론 AI 판 기록·추론·발언 설계안

작성일: 2026-09-30. 역할 추론·발언 계획은 설계 제안이며 성능 검증은 아직 하지 않았다. 정책 버전과 모델 실패 기록은 같은 날 로컬 코드에 추가했다. 근거는 `site/lib/game.mjs`, `site/lib/ai.mjs`, `site/app/api/game/route.ts`, `site/db/schema.ts`, `docs/observability.md`의 현재 작업 트리다.

## 1. 판마다 무엇을 남길까

현재 D1 `games.state`에는 역할 배정, 모든 제안과 공개 완료된 개인별 투표, 임무 결과, 채팅, 비공개 카드, 최종 승패가 들어 있다. `events`에는 수락된 행동의 게임 ID·버전·시각과 모델 토큰·지연이 있다. 로컬 변경에서는 새 판의 정책·모델 버전과 별도 `ai_failures` 테이블도 추가했다. 따라서 우선 **기존 상태를 판의 원본 기록**으로 삼고 별도 원문 로그를 중복 저장하지 않는다.

완료한 판마다 소유자 전용 평가 기능에서 아래 두 층을 만든다.

1. **판 요약:** 게임 ID, 규칙/AI 정책 버전, 모델 이름·설정, 시작 역할과 리더, 최종 승자·종료 이유, 제안·임무·채팅 횟수, AI 호출·토큰·지연, 오류·재시도 횟수. 일부 필드는 상태·이벤트·실패 기록에서 집계해야 하고, 규칙 버전·재시도 구분은 아직 없다. 게임의 역할 배정은 재현 조건을 위한 비공개 자료로 취급한다.
2. **시간순 사건:** `state_version`, 단계, 주체, 팀 제안·공개된 찬반·임무 결과·채팅의 사건 ID, AI 선택, 그때 참조한 공개 사건 ID. 게임 중에는 각 플레이어에게 허용된 정보만 보이고, 소유자용 전체 평가 자료는 게임 종료 후에만 제공한다. 사람의 원문 채팅과 비밀 정보는 공개용 요약에서 제외한다.

예시 판 요약(값은 형식 예시이며 실제 결과가 아님):

```json
{
  "gameId": "…", "policyVersion": "baseline-1", "model": "…",
  "initial": { "leader": "ai2", "rolesPrivate": "owner-only" },
  "outcome": { "winner": "GOOD", "reason": "assassination-miss" },
  "counts": { "proposals": 7, "quests": 3, "aiCalls": 0, "invalidActions": 0 },
  "usage": { "inputTokens": 0, "outputTokens": 0, "latencyMs": 0 }
}
```

예시 수치는 기록하지 않는다. 실제 구현 시 측정값을 채우고, 없는 값은 `null` 또는 `미측정`으로 둔다. 현재 `events`의 `game_id + version` 고유 제약은 **수락된 상태 전이**를 나타낸다. 상태가 바뀌지 않은 모델 오류·무효 응답은 별도 `ai_failures` 기록으로 구분한다. 오류 원문 프롬프트와 채팅 원문은 그 기록에 넣지 않는다. 보관·삭제 정책도 외부 사용자에게 공개하기 전에 정해야 한다.

## 2. 투표·임무를 모델에 줄까, 알고리즘으로 계산할까

현재 `observe()`는 제안과 임무 기록, 공개가 끝난 투표를 모델에 전달한다. `context()`는 제안을 최근 6개로 줄이고 메시지는 최근 8개로 줄인다. 그러므로 새로 원문 기록을 무조건 더 넣기보다, **전체 공개 이력에서 만든 검증 가능한 상태 요약**을 추가하는 실험이 적절하다.

같은 초기 조건에서 세 방식을 비교한다.

| 방식 | 입력과 결정 | 알아볼 것 |
| --- | --- | --- |
| A. 현재 정책 | 최근 공개 기록을 Gemini에 주고 행동을 직접 받음 | 기존 기준선 |
| B. 구조화된 추론 보조 | 공개 임무의 실패 카드 수와 자기 비밀 정보로 불가능한 5인 역할 배정을 제거하고, 후보 팀의 위험을 계산해 Gemini에 전달. 행동은 Gemini가 결정 | 계산 근거를 보고 선택을 개선하는지 |
| C. 점수 기반 행동 | B의 계산을 이용해 코드가 팀·투표 등 이산 행동을 선택. Gemini는 공개 가능한 설명과 대화를 담당 | LLM의 선택 오류를 줄이면서 대화 품질을 유지하는지 |

초기 계산은 정확한 논리만 사용한다. 임무에서 실패 카드가 `k`장이면 해당 팀에 악이 최소 `k`명 있어야 한다. 성공 임무는 악이 성공 카드를 냈을 수 있으므로 후보를 제거하지 않는다. 투표와 발언은 속임수·착오가 가능해 **확정 제약이 아니라 나중의 가중치 신호**다. 행동별 우열을 평가할 때는 역할별 승패, 5번째 제안의 자동 패배, 멀린 암살, 무효 행동과 비용을 함께 본다. 한두 판의 승률로 우열을 정하지 않는다.

## 3. 발언·행동 전에 앞말의 의도를 해석할까

도움이 될 수 있다. 특히 “왜 이 사람을 팀에 넣자고 했나”와 “실제로 누가 악인가”는 다른 질문이다. 다만 앞말의 의도를 모델이 **확정 사실처럼 믿으면** 악의 기만에 걸린다. 한 번의 자유로운 장문 추론이나 모든 AI의 별도 추가 호출보다, 현재 행동 호출 안에서 짧은 구조화 판단을 요청한다.

예: `무엇에 답하는가(message ID) → 확인된 공개 사실(event ID) → 가능한 해석 1~2개(추정) → 지금 필요한 행동/질문`. 해석은 `팀 설득`, `자기 방어`, `근거 요청`, `의심 돌리기`, `불명확` 같은 가설로 표현하고, 사실과 섞지 않는다. 상대가 거짓말할 수 있으므로 같은 발언을 두 방식으로 읽을 여지를 둔다. 판단 요약은 평가용 짧은 코드와 근거 ID 정도만 저장하고 모델의 긴 내부 추론 원문을 저장하지 않는다. 별도 해석 호출의 비용 대비 품질 향상은 비교 실험 전까지 미확인이다.

## 4. 근거 있는 발언을 어떻게 만들고 검사할까

발언을 자유 텍스트 한 덩어리로 받기 전에 **발언 계획**을 작게 만든다. 계획에는 `replyTo`, `evidenceIds`, `claimType`(질문/잠정 추론/팀 대안/반박/침묵), `intendedAction`을 둔다. 모델은 이를 바탕으로 1~2문장만 생성한다. 악의 의도적인 거짓 주장도 게임 전략으로 허용하되, 실제로 없던 제안·투표·임무를 인용하지 못하게 한다.

서버는 게시 전 다음을 확인한다.

1. 인용한 ID가 **그 시점에 해당 AI에게 공개된 사건**인지, `replyTo`가 실제 메시지인지 확인한다. 투표 중인 다른 사람의 표와 미공개 임무 카드는 근거 후보에 넣지 않는다.
2. 단계·역할에 맞는 행동인지와 발언 길이·형식을 검증한다. 반복되거나 없는 과거 사건을 단정하는 문장은 침묵 또는 재생성 후보로 처리한다.
3. 인용 사건과 문장의 **의미가 실제로 맞는지**, 비밀 역할을 간접적으로 노출하는지는 코드만으로 완전히 판정할 수 없으므로 준비한 사례와 실제 판을 사람이 표본 검토한다. 모델 검토기를 추가한다면 그 자체의 오류·호출 비용도 측정한다.

현재의 `unsupportedPastReference()` 정규식은 일부 표현만 막는다. 위 절차는 이를 대체할 구체적 계약이지만, 구현 전에는 효능을 주장하지 않는다. 검증 사례에는 `존재하지 않는 지난 투표`, `부결된 팀을 승인됐다고 말함`, `임무 전 미공개 카드 언급`, `질문 회피`, `동일 주장 반복`, `멀린의 과도한 확신`, `악의 자기 폭로`를 넣는다.

## 권장 첫 작업

다음 구현은 **한 판의 소유자 전용 JSON 내보내기와 요약 생성**이다. `games.state`, `events`, `ai_failures`에서 얻을 수 있는 필드로 실제 판을 확인하고, 판단 근거 기록은 역할 추론·발언 계획을 구현할 때 추가한다. 이후 A/B/C 비교와 발언 계획을 순서대로 시험한다.

## 2026-09-30 후속 판단: 의심 점수·문맥 범위·발언 태그

### 의심 카운트보다 역할 배정 후보

`수상한 행동마다 +1`은 구현과 설명이 쉽지만, 투표·팀 제안이 서로 의존하고 악도 선처럼 행동할 수 있어 점수가 과신으로 바뀌기 쉽다. 처음에는 60개 역할 배정 후보를 만들고 본인 비밀과 임무 실패 수로 **논리적으로 불가능한 후보만 제거**한다. 남은 배정에서 특정 팀에 악이 들어간 경우의 비율을 계산하되, 이는 행동 모델을 추가하기 전의 후보 비율이지 검증된 실제 확률은 아니다. `확정 악`은 역할 공개 또는 자기에게 허용된 확정 정보처럼 진짜 근거가 있을 때만 사용한다. 임무 실패에 참가했다는 사실만으로 확정하지 않는다.

투표·발언·팀 구성의 수상함은 후보를 지우지 않는 별도 **근거 목록**으로 둔다. 예: `proposal-3에 악이 있을 가능성이 높은 팀을 반복 포함`, `quest-2 실패 팀 참가`, `msg-7에서 설명 변경`. 나중에 충분한 판을 모아 행동의 신뢰도를 측정한 뒤 후보별 가중치나 승률 평가에 사용할 수 있다. 순위는 `왜 상위인지`를 사건 ID와 함께 보여준다. 별도 탐색 트리나 MCTS는 이 작은 후보 열거·행동 평가의 실패가 확인될 때 검토한다.

### 발언 전 참고 범위

모든 채팅을 무조건 넣기보다 사건에 맞춰 고른다: (1) 답할 메시지와 그 직접 답장, (2) 현재 팀 제안·투표 또는 방금 끝난 임무, (3) 같은 화자의 앞선 관련 발언과 변경점, (4) 최근 대화 일부. 오래된 사실인 제안·투표·임무는 원문 메시지 요약보다 구조화된 전체 이력에서 읽는다. 새 판 시작처럼 관련 발언이 없으면 없는 그대로 전달한다. 각 묶음에 사건 ID와 공개 시점을 붙이고, 모델에게 상대의 의도는 `가능한 해석`으로만 요청한다. 필요한 범위와 토큰 상한은 실제 질문 응답률·누락 사례로 조정한다.

### 발언과 태그 분리

`proposal`은 게임 엔진의 팀 제안 행동과 혼동되므로 발언 태그는 `speechAct`로 분리한다. 첫 버전은 `QUESTION`, `ANSWER`, `TEAM_SUGGESTION`, `CHALLENGE`, `DEFENSE`, `EVIDENCE`, `OTHER` 중 **주된 목적 하나**만 받고, `replyTo`·`evidenceIds`·`relatedProposalId`를 별도 필드로 둔다. 예: `{ "type":"CHAT", "text":"도윤, 이번 팀에서 하린을 뺀 이유가 있어?", "speechAct":"QUESTION", "replyTo":"msg-12", "evidenceIds":["proposal-3"] }`. 화면에는 `text`만 보이고 태그는 평가·대화 제어에 쓸 수 있다. 모델이 낸 태그는 자기 보고이므로 서버는 열거값과 공개 사건 ID만 확정적으로 검사할 수 있으며, 의미가 실제로 맞는지는 별도 표본 평가가 필요하다. 악의 허위 주장은 허용하되 존재하지 않는 사건 인용은 거부한다.

### 로컬 구현 상태

사용자 요청에 따라 `speechAct` 중 **주된 목적 하나**를 모든 `CHAT`의 필수 필드로 구현했다. 허용값은 위 일곱 가지이며 `site/lib/game.mjs`가 검증하고 메시지에 저장한다. AI는 발언과 태그를 함께 생성한다. 사람의 원문은 서버가 공개 대화·최근 제안·원정 문맥과 함께 Gemini에 보내 태그만 받아 붙인다. 분류 실패나 키가 없는 연습 모드에서는 원문을 보존하고 `OTHER`로 저장한다. 자동 태그는 의도·역할의 확정 근거로 사용하지 않는다. `evidenceIds`·`relatedProposalId`와 태그 의미 검증은 아직 미구현이다.

`site/lib/belief.mjs`는 60개 역할 배정을 만들고 **각 AI 자신의 관찰값**에서 역할·알려진 악·공개 임무 실패 카드 수와 모순되는 후보만 제거한다. 남은 후보 중 각 플레이어가 악인 배정의 비율뿐 아니라 완료 임무 팀과 현재 팀에 악이 0·1·2명인 후보 비율을 모델에게 비공개 단서로 준다. 예를 들어 충신이 아닌 두 사람의 팀에서 실패 카드가 하나 나왔다면 악이 0명인 후보는 제거하되, 악 둘 중 한 명만 실패 카드를 낸 경우도 남긴다. 이런 공동 제약은 플레이어별 비율만 읽으면 사라진다. 이는 `후보 중 비율`이며 아직 투표·발언의 우도, 악의 성공 카드 선택 확률, 상대 전략을 학습하지 않았다. 따라서 실제 악일 확률이 보정된 값이라고 주장할 수 없다. 나이브 베이즈처럼 서로 의존하는 투표와 발언을 독립 단서로 곱하지 않는다. 이후 평가용 판이 쌓이면 행동 유형별 우도를 별도 데이터에서 추정하고, 기존 정책과 같은 조건에서 비교한다.
