# 공개 근거와 구체적 선택을 연결하는 대화

## 관찰과 범위

사용자 첨부 판 `5b67dfb7-87f0-4577-a423-24b62833ef21`은 정책 .7, V2, A 방식이다. AI 메시지 14건(시작 자동 안내 1건 포함) 중 9건에 ‘신중’이 들어간다. 형식상 TEAM_SUGGESTION인 메시지에도 명단이 없고 반대 이유 질문에 참가자·원정 근거를 특정하지 않았다. HTTP429 3건과 4차 팀 선정 fallback 1건은 별도 장애이며 앞선 일반적 대화의 원인으로 단정하지 않는다.

후보 수정은 기존 토론 순서·팀 확정·투표 규칙을 변경하지 않는다. 사용자 V2 본문과 thinking 지시를 보존하고 CHAT 요청 JSON에 공개 토론 과제를 넣는다. 실제 평가 시 후보 정책은 .8로 표기했다. 품질 기준 미통과로 운영 연결을 제거했으며 현재 정책은 .7·V2다. 후보는 `buildDiscussionPrompt`로만 실행한다. 앞서 제안한 팀 초안·응답 예약·토론 종료 흐름은 별도 미구현 항목이다.

## 구현과 경계

- `site/lib/prompts/discussion.mjs`: 구체적 참가자/명단, 공개 근거(첫 원정은 검증 목적), 원하는 선택을 요구한다. 질문에는 직접 답하고 반복만 가능할 때는 침묵을 허용한다.
- 현재 팀과 공개 원정 결과, 본인의 이미 공개된 찬반 선택, 최근 본인 발언을 제공한다. 비밀 역할·known·전체 역할표·타인의 개별 카드·미공개 찬반을 복사하지 않는다.
- 과거 투표 당시 이유는 저장되지 않았다. 현재 공개 기록으로 재검토하는 설명을 요구하고 실제 기억이라고 꾸미지 않도록 명시한다. 공개 투표 설명 저장은 미구현이며 장기적으로 별도 개선이 필요하다.
- 생성 thinking은 기존대로 폐기하고 다음 모델 입력·화면·게임 로그에 포함하지 않는다.
- 단어 ‘신중’ 자체를 금지하거나 내용 검사로 자동 재시도를 늘리지 않는다. 내용 품질은 별도 실제 평가로 판단한다. 운영 생성 호출 수는 늘리지 않으며 입력 토큰은 늘어난다.

## 실제 모델 평가

`site/tests/live-discussion.mjs`: 외부 호출 상한을 명시적으로 설정하고 direct fetch로 자동 재시도를 하지 않는다. 입력은 첨부 판의 3개 시점을 재구성한다. 실제 전송 원문과 당시 입력의 완전 동일성은 확인할 수 없다. 시점 이후 원정/발언/제안은 제외한다. thinking·비밀 키·프롬프트 원문을 출력하지 않는다.

평가 상황: 첫 실패 후 서아의 팀 의견, 모두 참여한 상황에서 추리는 방법에 대한 지호 답변, 서아의 3차 반대 이유 질문. 기준은 (1) 구체적 참가자/팀 (2) 공개 근거 또는 근거 부족을 밝힌 검증 목적 (3) 선택 제안/질문 답변이다. 과거 마음을 지어낸 설명은 미통과로 본다. 역할 정체를 아는 분석자 관점의 전략 정확도와 분리한다.

최초 사용자 승인: 기존 3회 + 수정 3회, 총 6회. 모델 gemini-3.5-flash-lite, temperature 0.7, 출력 상한 768, V2 유지. 총 6회 모두 CHAT 형식으로 응답했다. 수정은 3개 중 1개만 기준을 충분히 충족했다(Codex 수동 평가). 나머지는 여전히 모호하거나 과거 이유를 지어내어 배포하지 않았다.

| 사례 | 기존 입력/출력 토큰 | 최초 수정 입력/출력 토큰 | 기존/수정 지연 ms |
|---|---|---|---|
| 첫 실패 후 | 2444/71 | 2816/153 | 1434/1650 |
| 추리는 방법 | 3249/98 | 3882/124 | 1250/1602 |
| 반대 이유 | 3867/115 | 4530/139 | 1482/1473 |

사용자는 추가 보정 후 같은 사례 최대 3회의 추가 실제 검사를 승인했다. 추가 검사 결과와 배포 여부는 아래에 기록한다. 각 상황당 1회이므로 반복 품질·승률·장기 비용 개선을 의미하지 않는다. 프롬프트 요청 정보가 달라진 전후 판은 기존 A/B 표본과 동일 조건으로 섞지 않는다.

### 추가 3회 결과와 중단 기준

추가 생성 총 3회·모두 CHAT 형식·자동 재시도 없음. 구체적인 이름/팀·근거·선택을 필수 요구 내용으로 강화했지만 Codex 평가에서 1/3만 충분히 충족했다.

| 사례 | 입력/출력 토큰 | 지연 ms | 내용 평가 |
|---|---|---|---|
| 첫 실패 후 | 2933/183 | 1838 | 통과: 실패 팀을 특정하고 자신·도윤·지호의 대안을 제안. 이 팀이 안전하다는 뜻은 아님 |
| 추리는 방법 | 4007/61 | 1303 | 미통과: 하린·도윤을 살펴보자는 표현에 그치고 추리는 방법·선택이 없음 |
| 반대 이유 | 4655/75 | 1243 | 미통과: 인원이 적어서 신중했다는 일반론 및 저장되지 않은 당시 이유를 회상하는 표현 |

총 승인 범위 9회 사용. 추가 호출은 미실시. 품질 통과 전 배포하지 않겠다는 사용자에게 알린 기준에 따라 배포하지 않았다. 최초 후보·보정 후보 각각 상황별 1회이며 품질 비율은 이 평가 사례의 수동 판단일 뿐 서비스 통계가 아니다.

후보의 운영 연결을 제거하고 기존 `.7` AI/V2 빌더로 복원했다. V1 회귀가 아니다. `discussion.mjs`, 모의 검사·명시 승인용 평가 스크립트와 이 문서만 후보 결과물로 남겼다. 검사 스크립트는 `AVALON_EVAL_LOG`, 인증 URL/토큰, `AVALON_EVAL_LIMIT=6` 또는 `AVALON_EVAL_MODE=followup`과 `AVALON_EVAL_LIMIT=3`으로 실행한다. 인증 토큰은 파일/명령 인수가 아니라 세션 환경에서만 공급하며 새로운 유료 실행에는 새로운 사용자 승인이 필요하다. 현재 스크립트는 보정 후보를 평가하며 최초 후보 문구는 앞선 패치 기록에 있다.

다음 설계는 팀 선정·찬반 출력에 짧은 공개 설명과 참조 사건을 함께 저장하고, 답변이 그 기록을 사용하도록 하는 것이다. 내부 thinking은 계속 제외한다. 공개 설명을 행동과 같은 시점에 작성하면 과거 이유를 사후에 지어내는 문제를 줄일 수 있으나 구현·실제 모델 검증은 미실시다. 설명에는 허위 주장/기만이 섞일 수 있으므로 진실 판정이나 내부 추론 기록으로 해석하지 않는다.
