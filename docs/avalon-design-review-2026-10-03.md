# 아발론 게임 경험과 디자인 개선 검토

2026-10-03 한국 시간 기준. 이 검토는 재미, 인지 부담, 요소 간 목적의 일관성, 아발론의 심리전을 기준으로 현재 로컬 게임을 평가한다. 가장 먼저 개선할 부분은 **사람의 발언이 상대의 반응과 선택으로 이어지는 과정**, 그리고 **그 판단에 필요한 공개 근거를 쉽게 비교하는 화면**이다. 아래 내용은 Codex의 제안이며 사용자 승인이나 효과 검증을 뜻하지 않는다.

## 검토 범위와 근거

- `http://127.0.0.1:5173/`의 기존 연습 판 원정 결과 화면과 펼친 원정 기록을 브라우저에서 확인했다. 새 판 생성·채팅·투표·게임 진행은 하지 않았다. 현재 모바일은 새로 실행하지 않았으며 `docs/review-assets/roundtable-mobile-2026-10-02.jpg`를 보조 자료로 봤다.
- 현재 실행은 원탁 정책 .8, V2-persona-evidence-v1이다. V3는 문맥 회수와 평가 사례를 포함한 후보이며 `ai.mjs`의 기본 실행에 연결되지 않았다. Spec 009의 과거 모델 평가를 현재 버전의 품질 측정으로 사용하지 않았다.
- `node --test site/tests/game.test.mjs site/tests/roundtable.test.mjs site/tests/ai.test.mjs`: 24/24 통과. 규칙·정보 경계·진행·모의 모델 검사이며 재미나 실제 모델 품질의 증거는 아니다.
- 이번 검토에서 실제 모델 호출, 새 대국 완주, 배포 사이트 재검증, 사용자 대상 사용성 실험은 미실시했다. 연습 AI의 반복 대사를 실제 Gemini의 현재 응답이라고 해석하지 않는다.

## 모든 요소가 따라야 할 목적

제안하는 중심 경험은 **불완전한 공개 근거로 사람을 판단하고, 말을 통해 원정대와 표에 영향을 주며, 자신의 역할에 필요한 비밀을 지키는 것**이다.

화면의 각 요소는 현재 상황 파악, 근거 비교, 특정 참가자와의 상호작용, 결정, 결과 이해 중 하나를 도와야 한다. 개발자용 기록 접근은 보조 위치로 이동할 수 있다. 아름다운 중세 장식도 이 다섯 기능을 방해하지 않는 범위에서 사용한다.

인지적으로 좋은 디자인은 여기서 규칙·상태·과거 사실을 찾는 불필요한 부담을 낮춘다는 의미다. 추리의 불확실성과 기만은 게임의 재미로 남긴다. 인지능력 향상이나 건강 효과를 주장하는 검토가 아니다. 공개 사실을 쉽게 찾아보게 하는 방향은 [NN/g의 재인과 회상 원칙](https://www.nngroup.com/articles/recognition-and-recall/)을 적용한 설계 제안이다.

아발론의 정체성은 멀린이 악을 알아도 정체를 숨겨야 한다는 긴장에 있다. 이는 [제작사 소개](https://indieboardsandcards.com/our-games/the-resistance-avalon/)에도 명시된다. UI가 숨은 역할이나 정답 확률을 대신 알려주는 방향은 이 목적과 충돌할 수 있다.

## 유지할 기반

현재 원탁 화면의 어두운 청록색과 금색, 고정된 참가자 순서, 리더 표식, 현재 팀 표시는 기본 분위기와 상태 파악에 도움이 된다. 공개 사건과 대화가 같은 공간에 있고, 역할을 따로 펼쳐 볼 수 있으며, 투표 전 팀을 수정할 수 있는 구조도 유지할 가치가 있다.

전원 제출 뒤 표를 공개하고 개별 임무 카드의 주인을 숨기는 경계는 중요하다. 사람에게 토론 종료와 결과 확인 시간을 주는 제어도 기존에 선택한 설계다. 아래 템포 개선을 이유로 이를 임의로 자동 진행으로 바꾸지 않는다.

## 개선 우선순위

P0은 핵심 상호작용의 오류, P1은 핵심 경험 개선, P2는 경험이 안정된 뒤의 보완을 뜻한다. 효과 크기는 아직 측정하지 않았다.

| 우선순위 | 개선점 | 주로 해결할 문제 |
| --- | --- | --- |
| P0 | 명시적으로 답장한 상대에게 질문 전달 | 대화 상대에 대한 사용자 제어가 깨짐 |
| P1 | AI의 반응과 후속 선택 연결 | 사람이 혼자 토론을 계속 작동시키는 느낌 |
| P1 | 공개 기록을 비교 가능한 근거판으로 배치 | 추리보다 기록 탐색과 기억에 드는 부담 |
| P1 | 대화와 현재 행동을 화면의 중심에 배치 | 대화와 결정 버튼이 첫 화면에서 밀려남 |
| P1 | 역할 목표와 승패 임박 상태 설명 | 무엇을 왜 결정하는지 불분명함 |
| P1 | 암살을 위한 마지막 토론과 결과 공개 흐름 | 결말의 심리전과 긴장이 약함 |
| P2 | 참가자 식별과 역할 독립 성향 표현 | 네 상대가 비슷한 말풍선으로 느껴짐 |
| P2 | 종료 후 사실에 기반한 짧은 복기 | 패배 이유를 이해하고 재도전할 계기가 약함 |

## 질문 상대를 정확히 유지하기

**확인한 사실:** `site/lib/ai.mjs:143`에서 본문에 등장한 이름을 ID 순서로 찾고, `:150`에서 명시적 답장 대상보다 우선한다. 오프라인으로 도윤의 발언에 답장을 달고 “하린을 포함한 이유는 뭐야?”를 보내자 응답자는 도윤이 아닌 하린이었다. 모델 호출 전의 라우팅 문제다.

**영향에 대한 판단:** 플레이어는 원하는 상대를 추궁하거나 협상할 수 있어야 한다. 다른 사람이 답하면 대화의 책임 관계가 흐려지고, 상대가 질문을 회피한 것인지 프로그램이 잘못 연결한 것인지 구별하기 어렵다.

**제안:** 명시적 `replyTo`를 우선한다. 답장이 없을 때 호명과 단순 언급을 구별하고, 여러 이름을 포함한 문장에서 ID 순서가 수신자를 결정하지 않게 한다. 참가자 카드에도 기존 답장 기능과 연결되는 질문 진입점을 둘 수 있다.

**검증:** 명시적 답장+제삼자 이름, 다중 이름, 직접 호명, 자기 발언에 대한 답장을 자동 사례로 만든다. 명시한 상대가 항상 응답 대상인지 검사한다. 애매한 호명을 새 LLM 분류 호출로 해결하기 전에 명시적 UI 대상 선택을 우선 검토한다.

## AI 토론을 후속 선택과 연결하기

**확인한 사실:** `site/lib/game.mjs:85`에서 AI CHAT 뒤 토론 대기가 해제된다. `site/lib/ai.mjs:13`의 별도 idle 기회는 8초 이후 단계당 최대 두 번이다. 발언자는 지목·이전 화자·메시지 수로 선택한다. AI의 새 질문이 상대에게 곧바로 응답 기회를 예약하는 구조는 아니다. AI 리더 팀의 재검토도 별도 요청에 의존한다. B 정책 충신의 최초 팀 계산은 모델과 대화를 우회한다.

**영향에 대한 판단:** 사람이 한 번 말한 뒤 상대끼리 방어·반박·협상이 이어지지 않으면 네 참가자와 게임하는 감각이 약해질 수 있다. 대화가 팀과 표에 영향을 주는지 드러나지 않으면 채팅을 생략해도 된다고 느낄 수 있다. 이는 구조에서 추론한 위험이며 현재 모델의 실제 대국에서 빈도를 측정하지 않았다.

**제안:** Spec 013의 응답 기회 큐와 문맥 회수를 이어서 검토한다. 질문받거나 주장에 직접 관련된 상대에게 응답 기회를 주고, AI 리더가 제안을 유지하거나 수정할 때 공개적으로 설명할 기회를 제공한다. 과거 약속·직접 질문·공개 표를 다시 참조할 수 있게 한다. 모든 발언에 이름·근거·대안 양식을 강제하거나 반드시 입장을 바꾸게 하지 않는다. 유지·기만·침묵도 역할과 상황에 따라 타당하다.

**검증:** 명시적 AI 질문→상대 응답 기회, 사람 개입 우선, 동일 상태 중복 호출 방지, 오래된 응답 폐기, 비밀 정보 경계를 자동 검사한다. 실제 품질은 V2/V3의 동일 상황·역할·모델 조건에서 질문→응답→선택 구간으로 비교한다. 무관한 답변, 존재하지 않은 사실, 기계적인 반복, 선택과 발언의 연결을 사람이 검토한다. 실패하면 후보를 기본 실행으로 전환하지 않는다. 호출 예산과 품질 통과 기준은 실행 전에 사용자와 정할 항목이다. 기존에 거부된 사건당 고정 발언 수 제한을 다시 도입하지 않는다.

## 공개 기록을 추리하는 자리에서 비교하기

**확인한 사실:** `site/app/page.tsx:138`의 전체 기록은 대화와 결정 영역 아래에 접혀 있다. 펼치면 제안들을 먼저, 원정들을 나중에 보여준다. 최근 원정은 상단과 대화 사건과 결과 영역에 반복된다. 초안 수정은 사건 텍스트로 남지만 기록 카드에는 최종 명단을 표시한다.

**제안:** 원정 단위로 제안·팀 변경·개인별 표·실패 카드 수를 묶고, 같은 참가자의 이전 표를 쉽게 비교하게 한다. 원정 트랙의 번호나 참가자 카드를 누르면 관련 공개 사실로 이동하도록 기존 기록을 재배치한다. 데스크톱에서는 대화 곁의 작은 근거 영역, 모바일에서는 읽던 대화 위치를 보존하는 기록 패널을 검토한다.

예를 들어 실패한 2인 팀의 명단과 찬성표를 나란히 보여주되 “하린이 악이다”라는 결론을 시스템이 써주지 않는다. 성공 팀도 악이 없었다고 확정하지 않는다. 개인 추리 메모는 후속 후보이며 먼저 기존 사실의 접근성을 개선한다.

**검증:** 사용자가 과거 특정 팀과 개인별 찬반을 찾아 현재 팀과 비교하는 과제를 수행하게 한다. 찾는 시간·잘못 읽은 횟수·대화 위치 복귀를 기존 UI와 비교한다. 공개 전 표·개별 카드·AI evidence가 나타나지 않는지는 자동 검사한다. 접근성 개선을 실제 추리 능력 향상으로 일반화하지 않는다.

## 대화와 현재 행동을 먼저 보이게 하기

**측정:** 로컬 브라우저의 1280×720 viewport, 원정 결과 화면, 문서 최상단에서 DOM 경계를 읽었다. `.messages`는 y=564.4~904.4, `.composer`는 y=623.4~720.0, `.decision-area`는 y=904.4~1043.2였다. 고정 입력창 위에 드러난 대화 영역은 약 59px이고 현재 결정 영역은 viewport 밖이었다. 이 한 화면의 측정이며 모든 기기와 상태에 동일하게 적용되는 수치는 아니다.

**제안:** 헤더·상태·참가자 영역의 세로 여백을 줄이고 원정 점수·리더·팀·지금 할 일을 압축해서 배치한다. 같은 최근 결과의 반복 표시를 줄인다. 현재 결정과 입력을 가까이 두되 서로 가리지 않도록 배치한다. 대화와 페이지의 이중 스크롤은 모바일에서 특히 재검토한다. 핵심 대사·투표·팀 이름부터 가독성을 확보하고 보조 글씨만 작게 한다.

`진단 로그`는 기록/설정 메뉴로 이동하고, 처리 상태는 화면 구석의 일반적인 “AI가 생각 중”보다 해당 자리에서 “도윤의 답변을 기다리는 중”처럼 표시하는 편을 검토한다. 단, 특정 AI가 답을 만들고 있다는 정보만 공개하고 미공개 선택이나 역할은 드러내지 않는다.

**검증:** 1280×720 및 모바일의 대표 viewport와 화면 키보드가 열린 상태에서 현재 팀, 최근 대화, 입력·결정 버튼을 확인한다. 확대·키보드 포커스·긴 이름·긴 대사도 확인한다. 합격 기준은 핵심 입력이 가려지지 않고, 사용자가 지금 가능한 행동과 대기 대상을 설명할 수 있는 것이다. 레이아웃 개편의 시안은 기존 색상과 참가자 순서를 유지해 먼저 비교한다.

## 역할과 위험을 선택 시점에 설명하기

**확인한 사실:** 역할 확인 화면은 역할 이름과 “당신이 아는 사람”을 보여주지만 선/악 소속, 역할별 목표, 그 사람들을 왜 아는지는 설명하지 않는다(`site/app/page.tsx:114`). 상태의 `제안 n / 5`는 다섯 번째 부결의 결과를 직접 알려주지 않는다. 단계 표시에는 임무 카드와 암살이 독립 단계로 없다.

**제안:** 역할 카드에 소속·승리 조건·본인이 아는 사실을 짧게 넣는다. 멀린은 “악 두 명을 알지만 암살당하면 패배”, 악은 “표시된 사람은 악 동료”, 충신은 “추가 정보 없이 공개 기록으로 판단”을 구분한다. 첫 행동 근처에만 필요한 규칙을 설명한다. 선의 성공 카드만 허용되는 이유와 악이 성공을 낼 수 있다는 사실도 해당 순간에 알린다.

상단에는 원정 성공·실패 수와 연속 부결 수를 구분한다. 다섯 번째 투표에서는 “이번 팀도 부결되면 악이 승리합니다”를 명시한다. 이는 반대를 금지하거나 정답을 추천하는 기능이 아니다. 세 번째 성공은 “암살을 피하면 선의 승리”로 연결한다. 상태를 드러내는 원칙은 [NN/g의 사용성 휴리스틱](https://www.nngroup.com/articles/ten-usability-heuristics/)을 참고했다.

**검증:** 처음 보는 사람이 자기 진영의 승리 조건, known의 의미, 다음 버튼의 결과를 설명할 수 있는지 확인한다. 역할별 문구와 4회/5회 부결 경계·세 번째 성공 상태는 자동 사례로 검사한다.

## 암살을 마지막 심리전으로 만들기

**확인한 사실:** 세 번째 성공의 CONTINUE 뒤 ASSASSINATE가 되고, AI 암살자는 다음 자동 요청에서 대상을 정한다(`game.mjs:154`, `ai.mjs:35`). UI에는 대기 설명이 있으나 마지막 토론을 위한 별도 진행 구간은 없다. 사람 암살자도 화면에서 후보 한 명을 누르면 선택을 제출한다. [Dized의 아발론 종료 규칙](https://rules.dized.com/game/rZluqS52QmGdpoVxcmVLtg/ZXYBfRlqRC2sEzECCLLmHA/ending-the-game-and-assassinating-merlin)은 마지막 논의 후 암살자의 지목을 설명한다.

**제안:** 세 번째 원정 성공→최종 논의→암살 대상 결정→정체 공개의 전환을 분명히 한다. 사람에게 기록을 돌아볼 시간을 주고 AI도 기존 공개 행동을 근거로 마지막 대화를 할 기회를 갖게 한다. 사람 암살자의 후보 선택과 최종 제출을 구분하면 오클릭 위험도 줄일 수 있다. 결과는 “원정은 세 번 성공했으나 멀린이 지목되어 악 승리”처럼 뒤집힌 이유를 보여준다.

**아발론의 느낌:** 금색 장식 추가보다 밀봉된 표의 동시 공개, 제출자 없는 카드 공개, 리더 표식의 이동, 마지막 지목처럼 규칙에서 생기는 긴장을 시각화하는 것이 효과가 있을 것으로 본다. 짧고 건너뛸 수 있는 연출을 쓰고 비밀 투표 방향·카드 제출자를 애니메이션 순서로 추측할 수 없게 한다. 역할과 무관한 초상·색상을 사용한다.

**검증:** 세 번째 성공 전 조기 암살 불가, 최종 논의 중 자동 지목 방지, 중복 제출 방지, 공개 전 정보 경계, 정지/재개와 사람 개입을 자동 검사한다. 실제 마지막 대화가 추리·은폐에 도움이 되는지는 별도 모델/사용자 평가다. 강제 타이머와 자동 종료 여부는 이번 제안에서 확정하지 않았다.

## 참가자 식별과 복기

**참가자:** 현재 아바타 색은 서로 다르지만 대화의 이름과 말풍선에는 그 대응이 약하다. 고정 색·작은 문양을 말풍선에도 연결하고 현재 발언자의 자리와 답장 대상을 가볍게 강조한다. 네 페르소나는 이미 있으므로 새 성향 시스템보다 실제 발언과 선택에서 차이가 보이는지 먼저 평가한다. 성향에 “항상 의심하는 악”, “항상 정답인 선” 같은 역할 힌트를 결합하지 않는다.

**복기:** 종료 화면은 승패·역할·암살 대상·JSON 다운로드 중심이다(`page.tsx:133`). 원정 실패 3회와 5회 연속 부결을 구체적으로 구별하고, 이번 판의 주요 팀 변경·엇갈린 표·실패 원정·암살 결과를 원문과 연결해 짧게 보여준다. 플레이어가 “어디에서 내 판단을 바꿀 수 있었는가”를 돌아볼 수 있게 한다. 진영 승률만으로 재미를 판단하지 않는다.

종료 로그 evidence를 사용한다면 “모델이 기록한 선택 설명”으로 표시한다. 이것을 AI의 진짜 의도나 인간의 속마음처럼 단정하지 않으며, 없는 과거 이유를 사후 생성하지 않는다. 플레이 중에는 계속 비공개로 유지한다. 검증은 종료 전 접근 차단, 사실·설명 구별, 누락 근거의 명시, 관련 사건 링크의 정확성을 포함한다.

## 실행 순서와 미확인 사항

먼저 답장 수신자 오류를 고치고, 역할·부결 경고·승패 사유처럼 작고 명확한 개선을 한다. 다음으로 기존 화면을 압축하고 기록을 판단 자리로 옮기는 시안을 비교한다. 대화 구조와 V3의 실제 모델 평가는 별도 작업으로 진행한다. 마지막으로 암살 흐름과 복기를 보완한다. 새 역할·인원·랭킹 등 범위 확장은 이 핵심 경험을 확인한 뒤 판단한다.

사람의 토론 종료·결과 확인 제어는 기존 선택을 유지하는 전제다. 확인 버튼을 없애거나 자동 진행시키는 변경, 대화 호출 예산, 마지막 토론 종료 방식은 구현 전 결정이 필요한 항목이다. 이번 검토는 이를 사용자 결정으로 확정하지 않았다.

실제 재미, 질문이 투표를 바꾼 인과 효과, 몰입도, 인지 부담 감소, 재플레이 의향의 개선은 미확인이다. 작은 사용성 비교에서는 같은 상황에서 근거 찾기·상태 이해·상대 지목을 관찰하고, 게임 후에는 기억에 남는 설득/배신 장면과 다시 하고 싶은 이유를 확인할 수 있다. 이 결과 없이 기능 수나 테스트 통과 수를 재미의 성과로 쓰지 않는다.
